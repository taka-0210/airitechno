# 既存サイトデータ 選別・移行計画

更新日: 2026-08-10  
移行元: `https://pro-chubo.com/`

## 1. 結論

既存サイトのデータは選別して新CMSへ移行できる。

ただし、旧データを新しい公開テーブルへ直接コピーしない。移行専用のステージング領域へ取り込み、内容、画像、権利、分類、移行先を確認してから公開データへ変換する。

## 2. 移行対象と対象外

### CMSへ移行する候補

- 店舗情報
- ブログ・お知らせ
- 導入・施工事例
- お客様の声
- サービス・特設ページ
- 固定ページ
- FAQ
- バナー
- 記事内画像、店舗画像、PDF等
- 旧URL、タイトル、公開日、SEO情報

### CMSへ移行しないもの

- 商品、在庫、価格、商品画像・動画: 厨房君APIを参照する
- 古い問い合わせ本文等の個人情報: 業務・保管要件を確認せず移行しない
- セッション、キャッシュ、アクセスログ
- 旧管理者のパスワード
- 一時ファイル、サムネイルの重複、生成キャッシュ

## 3. 必要な移行元

精度の高い移行には、次のいずれか、できれば両方を使用する。

1. **旧サイトのデータベースと画像ファイル**
   - 記事本文、公開日、分類、画像との対応を正確に取得できる
   - 非公開・下書き・旧ページも確認できる

2. **公開サイトの巡回データ**
   - 実際に公開されているURLと表示状態を確認できる
   - DB内の不要データと公開資産を区別できる

移行前にDB構造、文字コード、画像保存場所、URL生成規則を読み取り確認する。元データは変更しない。

## 4. 移行ステージの項目

各データを次の形式で保持する。

- 移行管理ID
- 旧システムの種別・ID
- 旧URL
- 旧タイトル
- 旧本文（原文）
- 旧公開日・更新日
- 旧カテゴリ・店舗情報
- 画像・添付ファイル一覧
- 取得元と取得日時
- 内容ハッシュ
- 文字コード変換結果
- 判定: ①そのまま／②2026年版へ進化／③不要・統合
- 新しいコンテンツ種別
- 移行先URL
- 対象店舗・地域・業種・サービス
- 編集担当者
- 確認状態
- 移行状態
- 備考

旧本文は監査・比較用に保持し、編集後本文とは分ける。

## 5. 選別フロー

`収集 → 自動分類 → 重複検出 → 人による判定 → 再編集 → プレビュー → 承認 → 本登録`

### 自動でできること

- URL、タイトル、本文、日付、画像の取得
- ページ形式や記事種別の推定
- 同一・類似ページの検出
- 古い住所、電話番号、会社名等の候補検出
- 店舗名、地域、業種、サービスのタグ候補生成
- リンク切れ、画像切れ、文字化けの検出
- 旧URLと新URLのリダイレクト候補作成

### 人が判断すること

- その内容を現在も会社として保証できるか
- 顧客名、写真、図面等を再公開してよいか
- 本部実績か、プロ厨房HIT全体の実績として扱えるか
- どの記事を統合し、どの記事を代表事例にするか
- 古い価格、制度、連絡先、サービス範囲の修正
- 3D・CAD・現場写真に説明を加える編集

## 6. 3分類ごとの移行方法

### ① そのまま使える

- 新CMSの項目へ機械変換する
- 表示崩れ、内部リンク、最新性を確認する
- 承認後に公開する
- 旧URLから新URLへ301転送する

### ② 2026年版へ進化

- 旧本文・画像を素材として取り込む
- 公開側には下書きとして登録する
- 新しいブランド方針と入力項目に沿って再編集する
- 店舗、サービス、業種、商品を関連付ける
- 事例は「課題・提案・施工・完成・声」の構成へ組み直す
- 承認後に公開する

### ③ 不要・統合

- 公開データへは登録しない
- 統合先と301転送先を記録する
- 元データと判定記録は移行監査用に保持する
- 画像は即時削除せず、未使用候補として隔離する

## 7. 画像・添付ファイル

- 元ファイルを先に収集し、記事本文だけを移行しない
- ファイルのハッシュで重複を検出する
- 旧URLと新保存先の対応表を作る
- 画像の代替テキストと権利・許諾を確認する
- 壊れた画像、極端に小さい画像、旧デザイン部品を分ける
- 未使用と判断したファイルは削除せず隔離する
- 公開時はコンテンツ別ディレクトリへ保存する

## 8. 文字コード・本文変換

旧サイトには、古いPHPページや文字コードの異なるデータが含まれる可能性がある。

- 元の文字コードを記録してUTF-8へ変換する
- 機種依存文字、半角カナ、文字化けを検出する
- インラインの装飾や旧HTMLを除去・変換する
- 電話番号、住所、営業時間を本文から店舗マスターへ置き換える
- 旧サイト固有の相対リンクを新URLへ変換する
- 変換前本文と変換後本文を比較できるようにする

## 9. 移行の実行単位

一括公開せず、次の順番で小さく移行する。

1. 店舗情報
2. 法定・取引条件ページ
3. 開業支援・厨房設計の代表ページ
4. 優先導入事例（まず10件程度）
5. 重要なお知らせ・お役立ち記事
6. 残りの記事
7. 旧ページの統合・転送

最初に代表的な10件程度で変換・確認方法を固めてから全件へ展開する。

## 10. 検証

- 移行元件数、判定件数、移行件数、除外件数が一致する
- 旧URLごとに公開、転送、廃止のいずれかが決まっている
- 画像・PDFが表示できる
- 顧客情報と公開許諾に問題がない
- 店舗、サービス、記事の関連付けが正しい
- 旧URLから新URLへ正しく転送される
- タイトル、説明、見出し、canonicalが正しい
- 文字化けや旧住所・旧電話番号が残っていない
- 商品データがCMSへ重複保存されていない

## 11. 安全な実施条件

- 旧サイトと旧DBは読み取り専用で扱う
- 作業前にDBと画像ファイルのバックアップを取得する
- 移行処理を再実行しても二重登録されないようにする
- 本番公開前にローカルまたは移行環境で確認する
- 既存URLのリダイレクト表を承認してから切り替える
- 個人情報、APIキー、DB認証情報を移行データやGitへ含めない

## 12. 次の作業

1. 旧サイトのDB構造と画像ディレクトリを読み取り調査する
2. 公開URLを収集し、DBレコードと照合する
3. 個別URL棚卸しCSVを生成する
4. 代表10件で移行試作を行う
5. CMSの店舗マスターを実装する
6. 店舗データから本登録を開始する
